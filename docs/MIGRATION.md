# انتقال از نسخهٔ قبلی

ZIP و پوشهٔ نسخهٔ قبلی تغییر داده نشده‌اند. برای انتقال، یک دیتابیس جدید PostgreSQL با نام متفاوت بساز. اجرای migration جدید روی دیتابیس قدیمی توصیه نمی‌شود؛ شکل چند ستون و روابط تغییر کرده است.

## نگاشت جدول‌ها

| نسخهٔ قبلی | نسخهٔ جدید | توضیح |
|---|---|---|
| `ok_accounts` | `ok_accounts` | کد، نام، حلقه، کارگروه؛ جایگزینی role با Booleanهای مستقل، افزودن شناسه بله، تعلیق، وضعیت فعال |
| `ok_admins` | `ok_accounts.is_admin` | رابطهٔ جانبی نقش به ستون کاربر منتقل می‌شود |
| `ok_growth` | همان نام | کلید ترکیبی عضو/روز و جزئیات JSONB حفظ می‌شود |
| `ok_posts` | همان نام | نوع، محتوا و پیوست‌ها در JSONB، نویسنده ForeignKey |
| `ok_votes` | همان نام | like/recommend/bookmark با کلید ترکیبی |
| `ok_comments`, `ok_comment_likes` | همان نام‌ها | پاسخ به دیدگاه، رابطه با عضو و پست |
| `ok_messages`, `ok_inbox`, `ok_grades` | همان نام‌ها | پیام، گیرندگان و امتیاز مربی |
| `ok_files`, `ok_upload_usage` | همان نام‌ها | متادیتا و سهمیه؛ بایت فایل جدا منتقل می‌شود |
| `ok_preferences`, `ok_notices`, `ok_follows` | همان نام‌ها | تنظیمات، اعلان، دنبال‌کردن |
| `ok_removed_posts`, `ok_revision` | همان نام‌ها | حذف مدیریتی و نسخهٔ داده؛ revision بازتولید می‌شود |
| `ok_sessions`, `ok_session_attendance` | `django_session` | نشست‌های قبلی منتقل نمی‌شوند؛ ورود مجدد لازم است |
| — | `ok_landing`, `ok_forms`, `ok_form_responses`, `ok_audit` | محتوای واقعی کارگروه، فرم‌ها و رخدادهای مدیریتی |

مدل‌های این نسخه مطابق دیتابیس واقعی بستهٔ قبلی‌اند؛ صرف نام‌بردن از یک مدل در گفتگو به معنای وجود آن در دیتابیس قبلی نیست. به‌ویژه برنامهٔ حلقه و جلسهٔ کارگروه در پست با نوع مخصوص نگهداری می‌شوند. مدل‌های مستقل Reels، مصوبات و رویداد کلیک در این انتقال ساخته نشده‌اند؛ ریلز همچنان «به‌زودی» است.

## ترتیب کار

۱. از دیتابیس قدیمی و پوشهٔ upload آن پشتیبان بگیر. تا پایان اعتبارسنجی، سرویس قدیمی را قابل بازگشت نگه دار.

۲. `DATABASE_URL` نسخهٔ جدید را به دیتابیس **تازه** بده. از پوشهٔ backend اجرا کن:

```bash
python manage.py migrate
```

ترتیب خودکار migrationها: migrationهای وابستهٔ Django، `core/0001_initial`، `core/0002_alter_user_password` و migration نشست با رعایت dependency. `0002` ظرفیت ستون رمز را برای هش قدیمی افزایش می‌دهد. هیچ migration دادهٔ نمایشی یا کاربر نمی‌سازد. از `--fake` استفاده نکن.

۳. قبل از import حساب نساز. متغیر `LEGACY_DATABASE_URL` را در محیط فرایند به دیتابیس قدیمی تنظیم کن؛ preferably با دسترسی فقط‌خواندنی. این متغیر از فایل env توسط خود فرمان خوانده نمی‌شود؛ باید environment واقعی فرایند باشد.

```bash
python manage.py import_legacy
```

این حالت dry-run است: منبع فقط‌خواندنی است، مقصد در تراکنش بررسی و rollback می‌شود. هش ناشناخته، کلید ناسازگار یا رکورد نامعتبر باید قبل از انتقال واقعی اصلاح/نگاشت شود. منبع را برای رفع خطا دستکاری نکن؛ از کپی آزمایشی استفاده کن.

۴. پس از بررسی dry-run و توقف نوشتن در نسخهٔ قبلی:

```bash
python manage.py import_legacy --apply
```

حساب‌های مربی از role قدیمی و ادمین از `ok_admins` تشخیص داده می‌شوند. اگر نقش مسئول حلقه/کارگروه در دیتابیس قبلی وجود نداشته، باید از پنل مدیر جدید تعیین شود؛ از روی نام فرد نقش حدس زده نمی‌شود. اگر ادمین قدیمی موجود نیست، بعد از import حساب ادمین واقعی را با `create_member --admin` بساز.

۵. **کل پوشهٔ فایل‌های بارگذاری‌شدهٔ قبلی** را با همان شناسه/نام‌های ذخیره‌شده به مسیر `UPLOADS_DIR` جدید کپی کن. تصاویر ثابت سایت همراه سورس هستند؛ این مرحله برای فایل‌های کاربران است. بدون این مرحله رکورد فایل منتقل شده ولی دانلود آن کار نخواهد کرد.

۶. تعداد کاربران، پست‌ها، گزارش‌ها، هش‌ها، امتیازها، پیام‌ها و چند پیوست نمونه را مقایسه کن. ورود عضو/مربی/ادمین واقعی و نقش‌های هم‌زمان را در staging آزمایش کن. رمز قدیمی پس از اولین ورود موفق از scrypt به Argon2 ارتقا می‌یابد؛ رمز خام منتقل یا نگهداری نمی‌شود.

۷. سرویس/دامنه را به نسخهٔ جدید تغییر بده. ورود مجدد کاربران لازم است. هنگام بازگشت به نسخهٔ قدیمی، نوشته‌های جدید منتقل‌شده پس از cutover خودکار همگام نمی‌شوند؛ قبل از rollback از مقصد هم پشتیبان بگیر.

این importer برای schema واقعی قبلی `ok_*` نوشته شده است، نه برای دیتابیس فرضی شامل مدل‌های متفاوت `core_*`. اجرای انتقال روی دادهٔ واقعی و شبکهٔ میزبان هنوز باید در staging تأیید شود.
