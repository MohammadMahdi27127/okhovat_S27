# استقرار اخوت در دارکوب؛ یک اپ وب، بدون اپ جدا برای Redis

این راهنما برای بستهٔ دارای `Dockerfile` است. React، Django/Gunicorn و Redis در یک کانتینر اجرا می‌شوند. PostgreSQL تنها سرویس جداگانهٔ موردنیاز است. ظاهر صفحات، مسیرهای کاربران، مدل‌ها، migrationها و فرمول‌های برنامه نسبت به زیپ قبلی تغییر نکرده‌اند.

## ۱. فایل‌ها در GitHub

زیپ را استخراج کن. **محتویات** پوشهٔ `okhovat-react-django` را در ریشهٔ مخزن بگذار. در صفحهٔ اصلی GitHub باید `Dockerfile`، `backend`، `frontend` و `deploy` را ببینی. فایل `.env` واقعی، کلید Google، دیتابیس و فایل‌های خصوصی را بارگذاری نکن. پس از push، در دارکوب گزینهٔ «منبع گیت» را انتخاب کن.

## ۲. PostgreSQL

یک دیتابیس PostgreSQL برای این نسخه تهیه کن. از نام کاربری/رمز/نام دیتابیس و **هاست داخلی** همان سرویس استفاده کن. اپ وب و دیتابیس باید روی شبکه‌ای باشند که به هم دسترسی دارد. برای دیتابیس خارجی TLS را طبق تنظیمات سرویس‌دهنده به URL اضافه کن.

اگر دیتابیس نسخهٔ FastAPI قدیمی اطلاعات دارد، این نسخه را مستقیماً روی همان schema اجرا نکن. ابتدا دیتابیس جدید بساز و طبق `MIGRATION.md` اطلاعات را انتقال بده. اگر قبلاً همین نسخهٔ Django را راه‌اندازی کرده‌ای، از دیتابیس مربوط به همان نسخه استفاده کن.

## ۳. تنظیمات ساخت اپ

| فیلد پنل | مقدار |
|---|---|
| نوع ساخت | منبع گیت |
| آدرس ریپو | آدرس مخزن خودت |
| نام برنچ | برنچ واقعی؛ معمولاً `main` |
| Build Context | `.` |
| آدرس Dockerfile | `./Dockerfile` |
| پورت سرویس | `8000` |
| دستور اجرایی و ورودی‌ها | هر دو خالی؛ از ENTRYPOINT ایمیج استفاده شود |
| Readiness Probe (HTTP) | `/api/health/` |
| تعداد نمونه/Replica | `1`؛ autoscaling غیرفعال |

اگر پوشهٔ پروژه را با همان نام داخل ریپو گذاشته‌ای، context باید همان پوشه باشد؛ تنظیمات جدول بالا برای حالتی است که Dockerfile در ریشهٔ مخزن است.

دستور اجرای پنل را به `gunicorn` تغییر نده؛ این کار راه‌اندازی Redis و migration را دور می‌زند. Supervisor هر دو فرایند را اجرا و در صورت خروج مجدداً راه‌اندازی می‌کند. Node فقط در مرحلهٔ build استفاده می‌شود و جزو فرایندهای در حال اجرای اپ نیست.

## ۴. متغیرهای محیطی اپ وب

مقادیر نمونه را جایگزین کن؛ رازها را در پنل نگه دار، نه Git:

```dotenv
DEBUG=False
SECRET_KEY=CHANGE_ME
ALLOWED_HOSTS=YOUR_DOMAIN
CSRF_TRUSTED_ORIGINS=https://YOUR_DOMAIN
DATABASE_URL=postgresql://DB_USER:URL_ENCODED_DB_PASSWORD@DB_PRIVATE_HOST:5432/DB_NAME
UPLOADS_DIR=/srv/okhovat/private-media
REDIS_URL=redis://127.0.0.1:6379/0
TRUST_PROXY_PROTO=False
TRUSTED_PROXY_COUNT=0
```

- `SECRET_KEY`: یک رشتهٔ تصادفی حداقل ۵۰ کاراکتری، ثابت بین دیپلوی‌ها. برای ساخت روی کامپیوتر خودت: `python -c "import secrets; print(secrets.token_urlsafe(64))"`. مقدار `CHANGE_ME` عمداً پذیرفته نمی‌شود.
- `ALLOWED_HOSTS`: دامنهٔ واقعی سایت بدون https یا مسیر؛ چند دامنه را با کاما جدا کن. دامنهٔ موقت دارکوب هم اگر استفاده می‌کنی باید اضافه شود.
- `CSRF_TRUSTED_ORIGINS`: همان دامنه‌ها با `https://`؛ نه اسلش پایانی و نه مسیر اضافی.
- `DATABASE_URL`: مشخصات واقعی PostgreSQL. رمز دارای کاراکتر رزروشده باید URL-encode شود. این هاست `127.0.0.1` نیست.
- `REDIS_URL`: دقیقاً مقدار بالا. خود Dockerfile هم همین مقدار پیش‌فرض را تعیین می‌کند؛ نیازی به ساخت Redis در پنل نیست.
- `UPLOADS_DIR`: مسیر دیسک دائمی کاربر، مطابق بخش بعد.
- `TRUST_PROXY_PROTO`: پس از تأیید اینکه پراکسی دارکوب هدر `X-Forwarded-Proto` را خودش بازنویسی می‌کند، مقدار `True` بگذار. اگر HTTPS در پراکسی terminate شود ولی این گزینه خاموش بماند، ممکن است redirect loop ببینی؛ روش صحیح تنظیم پراکسی است، نه خاموش‌کردن امنیت سایت.
- `TRUSTED_PROXY_COUNT`: فقط با تأیید تعداد پراکسی‌های مورد اعتماد و پاک‌سازی `X-Forwarded-For` تنظیم شود؛ برای یک پراکسی مورد اعتماد مقدار `1`. صفر پیش‌فرض امن است ولی پشت پراکسی می‌تواند محدودیت IP ورود را بین کاربران مشترک کند.

برای حضور در شیت خصوصی، `GOOGLE_APPLICATION_CREDENTIALS` باید به فایل service account که به‌صورت secret خصوصی mount شده اشاره کند؛ فایل را در image یا Git قرار نده. بدون آن، خواندن شیت عمومی مانند قبل انجام می‌شود.

## ۵. دیسک فایل‌ها

یک دیسک دائمی به `/srv/okhovat/private-media` متصل کن. کانتینر با کاربر غیرروت **UID/GID 10001** اجرا می‌شود؛ این مسیر باید برای این کاربر قابل نوشتن باشد. در تنظیمات امنیتی حجم/پاد از `fsGroup: 10001` یا تنظیم مالکیت معادل توسط پنل/پشتیبانی استفاده کن. برنامه هنگام شروع قابل‌نوشتن بودن مسیر را بررسی می‌کند و اگر درست نباشد خطای واضح می‌دهد.

این دیسک فقط برای عکس‌ها و پیوست‌های کاربران است؛ PostgreSQL دیسک/پشتیبان مستقل خودش را دارد. پوشهٔ uploads را مستقیماً از وب‌سرور عمومی نکن؛ دریافت فایل باید از API کنترل‌شده انجام شود.

## ۶. بعد از Deploy

شروع خودکار به ترتیب زیر است:

۱. بررسی تنظیمات، دسترسی نوشتن دیسک و اتصال PostgreSQL؛ در خطای شبکه چند بار با فاصله تلاش می‌شود.
۲. قفل هماهنگی migration در PostgreSQL، اجرای `migrate`، آزادکردن قفل، جمع‌آوری فایل‌های static و بررسی Django.
۳. اجرای Supervisor؛ Redis فقط روی loopback داخلی و Gunicorn روی پورت ۸۰۰۰ شروع می‌شوند.

برای migrationها از اتصال مستقیم PostgreSQL استفاده کن، نه transaction-pooling واسط، چون قفل هماهنگی از نوع session است. این قفل به معنی پشتیبانی از چند replica با Redis محلی نیست.

منتظر موفق‌شدن startup و readiness باش. اولین migration می‌تواند زمان ببرد؛ مهلت startup پلتفرم باید کافی باشد. در `/api/health/` پاسخ سالم `{"ok": true}` است. این مسیر فقط سلامت خدمات را نشان می‌دهد و عمداً برای probe داخلی HTTP و Host مربوط به IP پاد نیز کار می‌کند؛ صفحات دیگر همچنان HTTPS و کنترل Host دارند.

سپس در ترمینال اپ، که پوشهٔ کاری آن `/app/backend` است، حساب واقعی خودت را بساز:

```bash
python manage.py create_member --code YOUR_NUMERIC_CODE --name "نام خودت" --admin
```

رمز در ترمینال به‌صورت مخفی پرسیده می‌شود. هیچ حساب پیش‌فرض ساخته نشده است. برای انتقال داده، حساب اولیه نساز و ابتدا راهنمای migration را دنبال کن.

## Redis داخلی چه محدودیتی دارد؟

- اپ جداگانه و هزینهٔ سرویس جدا لازم ندارد؛ از CPU/RAM همان اپ استفاده می‌کند.
- فقط روی `127.0.0.1:6379` گوش می‌دهد؛ تنها پورت منتشرشده ۸۰۰۰ است. هیچ پورت، دامنه یا Service برای Redis در پنل نساز.
- کش ۱۵ دقیقه‌ای و شمارنده‌های محدودیت درخواست همان منطق قبلی را دارند. نشست هفت‌روزه در PostgreSQL است.
- کش و شمارنده‌ها با restart/reset پاک می‌شوند؛ گزارش‌ها، کاربران، پست‌ها و نشست‌ها پاک نمی‌شوند. هنگام deploy ممکن است دورهٔ محدودیت ورود از نو شروع شود.
- سقف دادهٔ Redis فعلاً ۱۲۸ MiB و سیاست `noeviction` است؛ شمارندهٔ امنیتی برای جا بازکردن بی‌صدا حذف نمی‌شود. مصرف کل فرایند Redis بیشتر از حجم دادهٔ آن است. اگر حافظه پر شود، نوشتن کش/شمارنده رد می‌شود و برخی APIها ۵۰۳ می‌دهند؛ مصرف را پایش کن. ظرفیت و تعداد workerها باید با پلن هماهنگ باشد.
- این بسته برای **یک replica** است. پیش از چندنمونه‌ای‌کردن اپ، Redis باید اشتراکی شود تا محدودیت ورود بین نمونه‌ها یکسان بماند. Redis داخلی در جایگزینی rolling ممکن است موقتاً برای هر پاد مستقل باشد.

## فایل‌های استقرار

- `Dockerfile`: build چندمرحله‌ای و اجرای غیرروت.
- `.dockerignore`: جلوگیری از ورود env، کلید، فایل کاربران و وابستگی‌های محلی به image.
- `.gitattributes`: حفظ پایان خط LF اسکریپت‌ها بعد از کار در Windows.
- `deploy/entrypoint.sh` و `prepare.py`: آماده‌سازی قبل از سرویس‌دهی.
- `deploy/supervisord.conf` و `redis.conf`: اجرای Redis و Gunicorn.
- `deploy/healthcheck.py`: healthcheck داخلی Docker؛ readiness دارکوب را نیز جدا طبق جدول تنظیم کن.

راهنماهای رسمی استفاده‌شده:

- https://docs.hamravesh.com/products/darkube/getting-started
- https://docs.docker.com/engine/containers/multi-service_container/
- https://supervisord.org/configuration.html

در محیط تهیهٔ این بسته Docker daemon در دسترس نبود؛ build/run واقعی image و اتصال به دیتابیس دارکوب هنوز باید در نخستین استقرار بررسی شود. این محدودیت به معنی انجام‌شدن تست واقعی نیست.

## نتیجهٔ بررسی این بسته

- ۲۲ تست بک‌اند موفق؛ شامل تست‌های قبلی و بررسی readiness، قطعی وابستگی و ترتیب/قفل migration.
- ۴ تست رابط کاربری موفق؛ TypeScript و Vite build موفق.
- بررسی migration: هیچ تغییر مدل بدون migration وجود ندارد.
- ۴۳ فایل فرانت‌اند، مدل‌ها و migrationها با زیپ قبلی بایت‌به‌بایت یکسان‌اند.
- syntax اسکریپت shell و پیکربندی Supervisor بررسی شد؛ مسیرهای فایل‌سیستم کانتینر برای بررسی syntax Supervisor موقتاً با مسیرهای فضای تست جایگزین شدند.
- Docker daemon، PostgreSQL و Redis واقعی در محیط آزمون در دسترس نبودند. تست خودکار از دیتابیس/کش ایزوله استفاده کرده است؛ ساخت و اجرای خود Docker image تأیید نشده است.
